## What is actually saved

The inspected native004 checkpoint has exactly five top-level keys: `actor_state_dict`, `critic_state_dict`, `optimizer_state_dict`, `iter`, `infos`. `infos` is null. The source-bound RSL5.0.1 `PPO.save/load` and `OnPolicyRunner.save/load` agree with this inventory. Native `CapsPPO` does not override save/load.

| State | Preserved now? | Continuation consequence |
|---|---|---|
| Actor/critic weights and learned18-action standard deviations | Yes | Strictly load all values. A continuation must bypass the existing repair loader's std=.1 overwrite. |
| Both observation normalizers' mean/variance/std/count | Yes, inside model dictionaries | Preserve all buffers, not merely network weights. Smoke has count45,516,288 for each normalizer. |
| Adam first/second moments, step counts, optimizer parameter-group options/LR | Yes | Actual smoke has17 state entries,40 Adam steps each and saved group LR1e-5. A continuation must not invoke the existing optimizer-reset initialization. |
| `PPO.learning_rate` Python scalar | **No** | RSL load restores optimizer groups, but not this scalar. The next adaptive minibatch writes the scalar back to every group. Restore it from an exact parent receipt and matching group LR before updating. Otherwise construction's5e-5 can replace a saved1e-5 starting point. |
| Native runner iteration label | Yes | It is the last completed loop label, not a full run-history counter. Native smoke starts1847 and saves1848 after2 updates. A fresh `learn` starts at the loaded label again. A continuation must explicitly define next label as parent last+1 and track additional versus cumulative updates independently. |
| Custom `CapsPPO.completed_updates`/diagnostic progress | **No** | Constructor resets it to0; resuming must set an explicit cumulative offset so progress/diagnostics cannot restart silently at1. |
| Global Python/NumPy/Torch CPU/CUDA RNG states | **No** | Seed values in the plan are initial conditions, not saved current generator states. Exact stochastic continuation cannot be recovered from the checkpoint. |
| CAPS private generator state and command-schedule private generator state | **No** | Both restart from constructor seeds without a new sidecar. Preserve/restore these in any future RNG-resumable protocol; never imply they were present in native004. |

Current sampled joint traces do not reconstruct all1024 environments. |
| Simulator state, contacts/solver warm-start caches, pending rollout/current observation and logger history | **No** | Current files cannot exactly reproduce the interrupted physical trajectory. Post-update checkpoints avoid needing a partially filled optimizer batch, but the next rollout still has missing physical/history state. |

`inspect_checkpoint.py` reproduces the binary-key/model/normalizer/Adam inventory using `torch.load(..., map_location='cpu', weights_only=True)` and verifies unchanged input bytes. `checkpoint_inventory.json` contains the actual details. The current repair path intentionally loads actor/critic/normalizers with `optimizer=False`, resets std=.1 and LR5e-5, and requires an empty optimizer: **it is not a resume path**.

## Smallest fresh-original longer allocation

Use a new immutable native/source/host version with one explicit fixed `pilot` budget **B chosen by root**, while keeping the existing2-update same-source smoke, six pilot phases,1024×24 dimensions, original checkpoint, objective, command schedule, physics, action/observation interface, adaptive rule and physical gates. Reusing the name `pilot` within a new version avoids an unnecessary new CLI mode; the source-bound selection already carries exact updates.

1. **`direct_config.py` + `build_source.py`:** change only the bound pilot update count/protocol/plan `training_iterations` and version identity. Keep replicas1024, controls24, seed/repair options and quiet1.0/moving.1/spatial.1 coefficients unchanged. The source map and host/native pins necessarily change; old artifacts remain intact.
2. **`direct_training.py` + `direct_contract.py`:** make the explicit immutable decision-update list belong to that selected allocation instead of fixed `[10,25,50]`; include the chosen final B. Validate exact additional updates,24B controls, final and decision checkpoint hashes, per-row raw evidence, reload, and expected diagnostic counts. Keep all applied-cap and evaluation checks unchanged. Retain the existing50 checkpoint as an early comparison point when B>50.
3. **`caps_ppo.py` only if later sparse gradients are required:** consume a declared sparse diagnostic-update list that includes the chosen final B. Existing code records every minibatch's KL/LR/loss but samples gradients only at1/10/25/50, so blindly extending B would provide no late gradient diagnosis. Reuse the existing diagnostic-on/off equivalence test; no loss, normalization, RNG or optimizer behavior changes.
4. **Host/guard/analyzer:** host's reported update count currently hardcodes2 or50; derive it from the verified selection. Keep phase ordering, RO inputs, exact owner cleanup/dual locks/weather restoration and independent initial/final constant/stop screens. Allocate an explicit training deadline and corresponding outer/fallback bounds from measured throughput/headroom. Bind the new source/plan/native/host and same-source smoke; do not silently accept the prior source's smoke. Analyzer changes only its source/selection/progress bounds, not scorers.

The initial50 controls/update sequence has the same declared initial conditions as the current matched run. This is more reproducible **as an experimental comparison**, not a promise of bitwise PhysX/GPU replay. A longer total limit does not change the current adaptive-LR rule or objective. Early decision checkpoints alone do not run cold evaluations; root still needs a separately bounded evaluation job if an early physical decision is required. No unreviewed automatic long continuation is implied.

## Optional learned-state continuation with explicit cold restart

This is more code and a different initialization comparison. Only use it if root chooses to preserve learned progress rather than rerun the original50 prefix. It can honestly preserve actor/critic/normalizers/Adam and progress lineage, while **declaring RNG/physical rollout restarted**, not pretending to satisfy exact RNG resume.

- Add an explicit initialization mode, preserving the original repair mode unchanged. Parent input is the completed, audited checkpoint and immutable parent campaign/receipt/source/decision hashes. Load all model/optimizer values strictly; preserve learned exploration std; restore `alg.learning_rate` from matching parent optimizer groups and receipt; restore cumulative custom update count; set the next native iteration label explicitly. Do not reuse `load_repair_checkpoint` for this mode.
- Require byte/value equality of actor, critic, both normalizers, Adam moments/steps/options, deterministic actions on a bound observation fixture, and LR scalar/group consistency **before any training rollout or optimizer step**. For progress, bind parent completed-update count, new additional budget and expected cumulative final count. Separate namespaces prevent native checkpoint filename collisions.
- Define a fresh seed tuple and cold reset for physical state, command schedule, action/observation history and CAPS pair cache. First pairs must be invalid; no stale previous episode state may enter the objective. Log that normalizer/Adam state is inherited while environment/RNG streams restart. Initial matched evaluations must use the selected parent checkpoint, with the preserved original baseline retained separately; current validators hardcode original checkpoint for `initial_*` and need an explicit input-checkpoint distinction.
- Add a small learner-state sidecar for **future** saved boundaries: cumulative updates, next iteration, LR scalar, all used global/private RNG states, algorithm/config/source/provenance and environment restart policy. A sidecar written now cannot recover the missing RNG at an already completed native004 checkpoint. Full uninterrupted simulator continuation would additionally need validated complete scene/history/caches snapshot semantics; that is outside this bounded next-learning task and is not recommended as a prerequisite.

Focused required CPU proof, only if this alternative is adopted: a real RSL loader checks complete state/Adam/LR equality from a deliberately non-default-LR checkpoint, detects tampered lineage, and validates explicit progress and first-pair reset semantics. A future sidecar can support split-vs-uninterrupted **synthetic** learner/RNG parity; that must not be advertised as PhysX trajectory equivalence.

## Capacity and budget decision

500 is an illustration, **not a chosen allocation**:12,288,000 transitions and240 nominal simulated seconds per environment, accumulated across the unchanged20-second episode resets. Linear scaling from the measured current50 learner is1,003.45 seconds; that is a sizing estimate, not an ETA. It already exceeds the existing600-second phase deadline. Total campaign guard/fallback also needs to include the five independent standing/evaluation phases, startup and cleanup margins.

Current save-every-update behavior would retain roughly2.19GB for500 native autosaves using the actual4,376,667-byte smoke checkpoint size, plus final/decision copies and raw evidence. Retained raw audit tensor payload alone scales to roughly1.31GB at500, excluding events, Python/tensor metadata, allocator reserve, simulator and transient export stacks. Current50 Torch peak is560,364,032 bytes allocated /620,756,992 reserved; these are not full-machine/PhysX headroom readings. Check actual headroom before allocation. A declared save cadence/streamed audit could reduce storage later, but changing those is not required just to establish the next fixed budget and should not become an open-ended telemetry rewrite. Preserve all required failure evidence.

For fastest decision now: wait for the current50 matched constant/stop result and sparse diagnostics, then choose **one** same-objective longer fresh-original budget or explicitly decline further budget if the evidence instead warrants an objective change. Fifty updates alone do not prove infeasibility. This proposal selects neither500 nor a resume strategy as an authorized runtime change.
