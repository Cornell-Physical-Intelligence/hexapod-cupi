Three CPU counterexamples were reproduced against the exact sensor-model snapshot supplied to the independent Claude terrain review (SHA `101f6a59…91336`). The source was not modified. These concern a reused preparation primitive; they are not observations of an already deployed terrain pipeline.

1. **Selective reset after inference capture/read fails.** `_DelayedStream.enqueue` clones pending payload/valid tensors inside the caller's inference context, and `read` stores inference tensors from `zeros_like`/`where`. Calling `reset([0])` outside that context raises PyTorch's in-place inference-tensor error. Allocate and update persistent sensor buffers under `torch.inference_mode(False)`, including pending validity masks, then add full/mixed-row reset tests across inference boundaries. Inspect IMU persistent bias state under the same rule; the current reproduction establishes the stream failure only.
2. **An older delivered frame overwrites a newer acquisition.** A legal custom transport (`period=.02`, `latency=.04`, `jitter=.04`) delivers capture .02 first, then capture0. `read` changes the held timestamp/value backwards. The shipped nominal cadence/jitter pairs do not by themselves reorder frames; this is an allowed latency-ablation failure. Update per-row held data only where the delivered acquisition is at least as recent as the last accepted acquisition, preserving dropout masks and an explicit equal-time tie rule. Test each row independently, including missing newer data for one row.
3. **The reused stream permits clock rewind.** After reading capture1 at1.01, a read at.5 reports age−.5 and valid=true. The new observation-mode adapter already rejects nonmonotonic assembly; the reused sensor transport does not. Validate a finite monotonic transport clock and finite captures before connecting it. This is a missing input guard, not evidence of an actual timestamp rewind in a robot run.
